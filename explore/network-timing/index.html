为什么这个网页
这么慢？

同样等了两秒，有时服务器还在算，有时图片已经开始下了。这里把一次页面加载拆成几个资源和几段等待，让你根据瀑布图找瓶颈。

先看总耗时，再找等待在哪

试试「主文档处理慢」和「图片下载慢」。总耗时都接近两秒，首字节出现的时间与最后完成的资源却不同。点资源名可以逐段读数。

教学模型。五个资源同源，HTML 结束后才发现样式、图片和脚本，脚本结束后才请求数据。主文档承担首次连接开销，其他请求复用该连接。并行资源使用各自的有效速率，模型省略共享带宽、浏览器渲染、流优先级和重试细节。勾选恢复会给图片下载增加一次 RTT。

怎么读图？

  1. 先找首字节。 如果 HTML 的等待阶段特别长，可能是请求往返或服务端处理慢。可用服务端计时辅助判断。
  2. 再找最后完成的资源。 首字节快，整体仍可能慢。对照下载条的长度和资源大小，再检查该资源什么时候才被发现。
  3. 观察复用省掉了什么。 DNS 缓存省的是查询，连接复用省的是握手，资源缓存省的是网络传输。它们对应不同的记录。

用浏览器核对自己的观测

打开自己控制的页面，在开发者工具的 Network 面板选中一个请求并查看 Timing。记录协议、请求发起原因和各阶段时长，再比较首次与重复加载。禁用 HTTP 缓存后仍可能复用现有连接或 DNS 缓存。Timing 中的等待时间从发出请求附近开始，别和本实验从整次加载起点统计的文档首字节耗时混用。真实页面还可对照最大内容绘制时间、服务端计时和响应大小。
